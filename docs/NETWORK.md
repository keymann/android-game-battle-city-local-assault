# 로컬 멀티플레이

계획서 §4 · §28 · §35 · §36 · §37 · §38 을 옮긴 것이다. 인터넷 서버를 쓰지 않고
같은 공유기 아래에서만 붙는다.

| 파일 | 맡은 일 |
|---|---|
| `net/Protocol.kt` | 패킷 종류와 상수 |
| `net/Packet.kt` | 바이트를 쓰고 읽는 최소 도구 |
| `net/Messages.kt` | 주고받는 내용과 인코딩 |
| `net/Transport.kt` · `net/UdpTransport.kt` | 패킷이 오가는 통로 |
| `net/LobbyState.kt` | 자리 · 준비 · 카운트다운 |
| `net/HostSession.kt` · `net/ClientSession.kt` | 접속과 동기화 |
| `net/SnapshotBridge.kt` | 게임 상태 ↔ 패킷 |
| `net/RoomScanner.kt` | 메뉴에서 방을 세어만 본다 (들어가지 않는다) |
| `game/NetDriver.kt` | 게임 루프와 세션을 잇는 자리 |

---

## 1. Host 가 권위를 갖는다

```
Client -> Host   INPUT       방향 / 발사 / 특수기
Host -> Client   SNAPSHOT    탱크 / 포탄 / 본진 / 점수 / 국면
Client -> Host   PRESENCE    결과 화면에 있다 / 떠났다
양쪽             PING/PONG   왕복 시간 측정
```

COM 생성과 AI, 충돌 판정, 탄환 판정은 전부 Host 에서만 한다. (계획서 §4.2)
Client 는 `BattleScene` 을 규칙 없이 굴린다 — 이동도 충돌도 하지 않고, 받은 상태를
얹어 그리기만 한다. 폭발 애니메이션만 스스로 흘려보낸다.

승패도 Client 가 계산하지 않는다. Host 가 내려 준 국면과 점수를 그대로 적는다.
"Host 가 게임의 최종 결과를 결정한다"(§35)를 코드로 지키려면 그 수밖에 없다.

---

## 2. 맵은 보내지 않는다

스테이지는 seed 하나로 어느 기기에서나 똑같이 만들어진다. 그래서 START 에 seed 와
`gridHash` 만 실어 보내고 Client 가 같은 맵을 스스로 만든다. 수백 KB 를 아끼고,
해시가 어긋나면 그 자리에서 알아차린다.

이것이 Phase 5.5 까지 결정론을 지켜 온 값이다. 난수기를 `Rng` 하나로 고정하고
variation 을 좌표 해시로 고른 덕에, 맵 전송이라는 큰 덩어리가 통째로 사라졌다.

---

## 3. TCP 가 아니라 UDP

20Hz 로 흘려보내는 상태 스냅샷은 **최신 것만 쓸모가 있다.** TCP 는 빠진 패킷을 다시
보내느라 그 뒤를 전부 붙잡아 두는데, 그러면 늦게 도착한 옛 상태 때문에 화면이 뒤로
튄다. 잃어버린 스냅샷은 다음 것으로 덮으면 그만이다.

`DatagramSocket` 이 아니라 `DatagramChannel` 을 논블로킹으로 쓴다. 소켓에는 진짜
논블로킹 모드가 없어서 1ms 타임아웃으로 흉내 내야 했는데, 그렇게 만든 첫 판은
기기에서 패킷을 한 장도 못 건졌다. 60Hz 루프 안에서 부르는 코드라 한 순간도
붙잡히면 안 된다.

### 패킷 크기

스냅샷 하나가 한 장에 들어가야 한다. 쪼개지면 UDP 에서 한 조각만 잃어도 통째로
못 쓴다. 좌표는 0.25px 단위로 접어 2바이트에 담는다. 탱크 16대 + 포탄 32발 +
점수 4줄을 다 채워도 MTU 안이다.

---

## 4. 20Hz 상태를 60Hz 화면에 붙이기

Client 는 마지막 두 장을 들고 그 사이를 메워 그린다. 방금 받은 장면을 곧바로 그리지
않고 **한 간격 뒤에서 따라간다.** 최신 것을 바로 그리면 다음 장이 올 때까지 그릴
것이 없어 멈췄다가 튄다. 대신 화면은 50ms 만큼 과거다.

다음 장이 늦으면 최신 위치에서 멈춘다. 앞질러 갔다가 되돌아오는 것보다 덜 거슬린다.

---

## 5. 로비 (계획서 §28, §38)

Host 는 언제나 0번 자리다. 방을 연 사람이 곧 권위다. 최소 두 명이 모두 준비해야
시작할 수 있고, 누구든 준비를 물리면 카운트다운이 멈춘다. 카운트다운이 끝나는
순간 Host 가 START 를 뿌리고 그 seed 로 모두가 같은 판을 연다.

조작 UI 는 Phase 7 에서 들어온다. 그때까지는 들어오면 곧 준비된 것으로 보고,
인원이 차면 Host 가 스스로 시작한다.

---

## 6. 끊김 (계획서 §37)

| 상황 | 처리 |
|---|---|
| Client 가 조용해짐 | 4초 뒤 자리를 비운다. 남은 사람은 계속한다 |
| Client 가 나간다고 알림 | 곧바로 자리를 비운다 |
| Host 가 방을 닫음 | Client 는 로비로 돌아간다 |
| Host 가 조용해짐 | 4초 뒤 끊긴 것으로 본다 |

Host Migration 은 만들지 않는다. 계획서가 초기 버전에서는 하지 않기로 정했다.

---

## 7. 무엇으로 확인했나

**단위 테스트 40개.** 통로를 갈아 끼울 수 있게 만들어 두어서, 메모리 안에서
Host 와 Client 를 함께 돌린다. 시간도 손으로 돌리므로 "4초 동안 소식이 없으면"을
4초를 기다리지 않고 확인한다. 패킷을 일부러 잃어버리게 해 첫 입장 패킷이 사라져도
다시 보내 들어가는지도 본다.

**기기 자체 점검.** 단위 테스트는 진짜 소켓을 쓰지 않으므로 안드로이드 권한과 실제
바이트 흐름은 확인하지 못한다. 그 부분만 기기에서 한 번 더 본다.

```bash
adb shell am start -n com.kophas.battlecity/.MainActivity --ez netSelfTest true
# I BattleCity: UDP 자체 점검 통과 자리=1 시작=true 스냅샷탱크=2
```

**기기 두 대.** 조작 UI 가 없어 아직 사람이 붙는 대전은 확인하지 못했다.

```bash
adb -s 기기A shell am start -n com.kophas.battlecity/.MainActivity --es netRole host
adb -s 기기B shell am start -n com.kophas.battlecity/.MainActivity \
    --es netRole client --es hostAddress 192.168.0.5
```

에뮬레이터끼리는 서로를 볼 수 없어(각자 NAT 뒤에 있다) 이 확인은 실기가 필요하다.

## 8. 로비 화면 (Phase 7 에서 붙였다)

`game/LobbyScene.kt` 가 그린다. Host 는 자기 `LobbyState` 를, Client 는 받은
`LOBBY` 패킷을 같은 모양(`LobbyScene.View`)으로 채워 넣는다.

- 자기 자리를 누르면 준비 상태가 바뀐다. 남의 자리는 눌러도 소용없다
- START 는 Host 에게만 살아 있고, 두 명 이상이 모두 준비해야 눌린다
- 누르면 3 → 2 → 1 → GO 를 세고 그 순간의 seed 로 모두가 같은 판을 연다

Phase 6 에서는 조작 UI 가 없어 "들어오면 곧 준비된 것으로 보고 인원이 차면 스스로
시작" 하게 두었는데, 그 임시 규칙은 걷어냈다.

## 9. 로비에서 고르는 것 (계획서 §29)

이름 · 탱크 종류 · 색을 고른다. 셋은 `READY` 패킷 하나에 함께 실려 간다. 따로 보내면
순서가 뒤바뀌었을 때 "이름만 바뀌고 색은 옛것" 같은 상태가 생긴다.

- **이름**은 세 글자다. HUD 한 칸에 들어가야 한다. 비우면 자리 번호로 `P1`~`P4` 가 들어간다
- **색**은 사람끼리 겹칠 수 없다. 이미 쓰는 색을 고르면 Host 가 **조용히 되돌린다.**
  거절하고 오류를 띄우면, 두 사람이 같은 순간에 같은 색을 누르는 흔한 일마다
  로비가 시끄러워진다
- **COM 색**은 하나로 고정하고 사람은 그 색을 고를 수 없다. 적아 구분이 안 되면
  게임이 성립하지 않는다

탱크 그림은 아틀라스에 **무채색**으로 들어 있다. 색이 박힌 그림에 다른 색을 곱하면
탁해지기 때문이다. 그릴 때 고른 색을 곱한다.

## 방 규칙과 결과 화면

START 한 통에 seed 와 함께 **방 규칙**(맵 크기 · 아군 오사 · 본진 보호 · 동시 COM 수)이
실린다. 맵을 seed 로만 보내므로 규칙이 한 사람이라도 다르면 다른 맵이 만들어진다.
그래서 참가자가 고른 값은 START 를 받는 순간 통째로 덮어써진다.

판이 끝나면 참가자가 `PRESENCE` 로 결과 화면에 있는지 알린다. 방장은 이것을 세어
PLAY AGAIN 을 열어 둘지 정한다. 남은 사람이 없으면 다시 열어 봐야 최소 인원을
못 채우므로 방장에게도 잠근다.

왕복 시간은 `PING` 에 **보낸 쪽의 시계**를 실어 보내고 받은 쪽이 그대로 돌려준다.
두 기기의 시계를 맞출 필요가 없다 — 값을 해석하는 쪽이 언제나 보낸 쪽이다.

자세한 것은 [SCREENS.md](SCREENS.md) 에 있다.
